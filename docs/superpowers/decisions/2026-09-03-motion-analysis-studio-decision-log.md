# Motion Analysis Studio 决策记录

## D-001：采用干净重建而不是直接重放历史补丁

状态：已接受。

原因：旧工作区源码不可用；会话日志中的补丁可以提供需求证据，但直接重放会重新引入旧实现的耦合和已发现缺陷。新文档作为唯一事实来源，重建结果可独立验证。

影响：需要重新建立阶段 1～9 的基础代码；必须在每个阶段建立 Git 提交和源码归档。

## D-002：阶段顺序采用质量保障到工程交付

状态：已接受。

顺序：阶段 1 三维质量检查；阶段 2 二维修正；阶段 3 标定诊断；阶段 4 同步；阶段 5 多人关联；阶段 6 运动学；阶段 7 事件周期；阶段 8 对比报告；阶段 9 工程化交付。

原因：二维修正依赖质量问题和时间轴，人物关联依赖同步，运动学依赖稳定 3D 结果；按此顺序可减少错误跨层传播。

## D-003：同步偏移必须数据驱动

状态：已接受。

原因：历史测试中 cam03/cam04 出现约负偏移，这可能是 Pose2Sim synchronization 的正常产物，不能当作固定规则。系统必须读取映射表、时间戳或配置，并显示来源。

影响：业务代码禁止按相机名返回固定偏移；映射缺失时必须阻塞精确跳转。

## D-004：人物身份与数组下标分离

状态：已接受。

原因：二维数组顺序会变化，Pose2Sim 轨迹段也不等于项目人物。系统区分项目人物、原始检测人物、关联人物和轨迹段；自动候选不能直接变成身份结论。

影响：多人关联需要骨架指纹、时间连续性和人工确认；多候选时禁用应用。

## D-005：关节点使用名称和模型映射

状态：已接受。

原因：质量报告的关节点顺序可能与二维模型顺序不同；历史问题曾出现报告中 Hip 被当成另一个裸索引。所有跨层定位必须经过名称映射。

影响：无法匹配名称时显示阻塞原因，禁止自动改点。

## D-006：工作界面采用可调分栏和滚动容器

状态：已接受。

原因：二维修正和三维质检信息量大，固定窗口会造成拥挤、截断和频繁上下滑动。QSplitter 保证主要区域可按用户习惯调整，QScrollArea 保证窄窗口仍可访问所有控件。

影响：必须有 1120×720 和 620×480 两组 GUI 门禁；布局不能依赖绝对坐标。

## D-007：所有长任务后台执行

状态：已接受。

原因：视频解码、JSON 扫描、Pose2Sim 子进程和指标计算的耗时具有数据规模依赖，放入 GUI 线程会造成不可接受的冻结。

影响：所有任务带 project_id、generation 和 task_id；切换项目后旧结果不得更新当前界面。

## D-008：保存和重跑分离

状态：已接受。

原因：人工保存应可快速验证，不应因一次保存意外启动外部计算；重跑必须由用户明确发起并只运行真正受影响的下游阶段。

影响：阶段图和允许列表双重校验；保存失败不得破坏原 JSON。

## D-009：保留功能指纹，但不要求交付 SHA-256

状态：已接受。

原因：标定导入需要判断文件内容是否真正变化，因此保留用于业务判断的内容指纹。用户已明确不要求每次文件改动后检查 SHA-256，因此不把发布哈希校验作为门禁。

影响：测试只验证导入内容变化和事务正确性；发布流程不要求向用户展示哈希。

## D-010：测试采用 unittest

状态：已接受。

原因：当前虚拟环境未安装 pytest，且标准库测试足以覆盖领域、文件和集成行为。GUI 性能使用 Qt heartbeat 测试。

影响：所有计划命令使用 python -m unittest；不自动安装 pytest。

## D-011：真实项目只用副本

状态：已接受。

原因：真实项目包含原始视频和用户已有结果，任何验收失败都不能污染原始数据。

影响：验收脚本必须复制到唯一临时目录，运行前后检查原目录文件和时间戳。

## D-012：文档与源码归档先于下一阶段

状态：已接受。

原因：本次工作区丢失表明仅依赖未提交工作树不安全。

影响：每阶段建立 Git 提交、源码归档、测试记录和已知限制；恢复计划是阶段门禁的一部分。
